vibedev agent workflow report
=============================

Scope
-----
This report describes the current package code under src/vibedev, with tests
and docs used as supporting evidence. It focuses on how vibedev starts agents,
how roles are selected, how information moves between agents, how pass/fail
verification works, and what files persist workflow state.


1. Public entry points
----------------------
The public Python API is exported from src/vibedev/__init__.py:

- prompt(...)
- set_permissions(...)
- set_model(...)
- set_workspace_root(...)
- set_team(...)
- set_common_knowledge(...)
- get_config()

The CLI entry point is src/vibedev/cli.py. It parses the user prompt and flags
for model, permissions, workspace root, per-run workspace, quiet mode, and
--no-common-knowledge. It then calls vibedev.core.prompt(...).

The package is a wrapper around claude-agent-sdk. It does not implement the
low-level tool loop itself. Claude Code / claude-agent-sdk owns model turns,
tool execution, file editing, and shell commands once query(...) is called.


2. Configuration and team setup
-------------------------------
Configuration lives in a module-level dict in src/vibedev/config.py.

Current defaults:

- permission_mode: bypassPermissions
- model: claude-opus-4-7
- workspace_root: ./vibedev-output
- common_knowledge: True
- team: [("developer", None)]

set_team(...) accepts a non-empty list of role names or (role, model) tuples.
Bare roles inherit the main model from set_model(...). Tuple entries override
the model for that role.

Example:

    vibedev.set_team([
        ("business_analyst", "opus"),
        ("developer", "haiku"),
        ("quality_assurance", "sonnet"),
        ("tester", "sonnet"),
    ])

The public validator in config.py currently accepts only:

- business_analyst
- developer
- quality_assurance
- tester

manager is intentionally rejected because it is implicit. An empty team is now
rejected; there is no no-team solo orchestrator path.


3. Runtime entry flow
---------------------
The main runtime function is vibedev.core.prompt(...).

It does this:

1. Validates the user prompt is a non-empty string.
2. Snapshots config with get_config().
3. Resolves and creates the workspace with ensure_workspace(...).
4. Prepares two log paths next to the workspace:
   - <workspace>.vibedev-logs/<UTC>.log
   - <workspace>.vibedev-logs/<UTC>.conversation.md
5. Prints run metadata unless quiet=True.
6. Bridges into async code with anyio.run(_run, ...).
7. Returns the workspace path when the run completes.

ensure_workspace(...) resolves the workspace path, creates it if needed, and
uses that exact directory as the agent cwd. There is no timestamped subfolder.
This makes repeated runs resumable, but also means generated files accumulate
in the same workspace.


4. The two deployment modes
---------------------------
vibedev currently has two agent deployment paths.


4.1 Coded team workflow
-----------------------
This path is selected when the configured team contains both developer and
tester. The function _supports_coded_team_workflow(...) checks only for the
presence of those role names.

In this mode Python owns orchestration. It does not give the manager a team and
ask the model to coordinate. Instead, core.py makes separate query(...) calls
for each stage:

- optional internal knowledge curator
- optional business analyst
- developer
- tester
- README updater after a passing test verdict

Each stage gets ClaudeAgentOptions from _options_for_role(...), with:

- cwd set to the generated workspace
- permission_mode from config
- model resolved for that role
- system_prompt set to the role prompt

Only the first configured developer model and first configured tester model are
used in this coded workflow. Duplicate developer/tester entries matter more in
fallback manager mode than in coded workflow.


4.2 Fallback manager workflow
-----------------------------
This path is selected when the team is non-empty but does not contain both
developer and tester. The default team of one developer uses this path.

core.py builds ClaudeAgentOptions with:

- system_prompt=build_manager_prompt(...)
- agents=subagents_for(...)

build_manager_prompt(...) renders a manager prompt listing the available team
members. subagents_for(...) builds the AgentDefinition dict for the SDK. If a
role appears more than once, roles.py assigns unique keys like developer,
developer-2, developer-3.

In fallback mode, the main model is a manager. It may delegate to SDK-native
subagents. With multiple team members, the prompt explicitly says it may issue
multiple Task calls in parallel for independent subtasks.

Fallback mode is intentionally less strict than coded team mode. It tells the
manager to use the available team members, verify what it can, and report
limitations. It does not enforce the developer/tester pass gate in Python.


5. Role catalog
---------------
src/vibedev/roles.py stores the role prompts and AgentDefinition templates.

Current role prompts:

- BUSINESS_ANALYST_PROMPT
- KNOWLEDGE_CURATOR_PROMPT
- DEVELOPER_PROMPT
- TESTER_PROMPT
- QUALITY_ASSURANCE_PROMPT
- fallback manager prompt template

SUBAGENT_ROLES currently includes:

- quality_assurance
- business_analyst
- developer
- tester

The knowledge curator is intentionally not in SUBAGENT_ROLES. It is an internal
ad hoc role run by Python at the beginning of coded developer/tester runs when
common knowledge is enabled.

The developer prompt says the developer receives one concrete task, edits files,
runs commands, and reports what changed and what the tester should verify.

The tester prompt says the tester receives one task plus the developer report,
verifies the changed scope, writes/runs tests when useful, and must end with a
machine-readable verdict line:

    VIBEDEV_VERDICT: PASS

or:

    VIBEDEV_VERDICT: FAIL


6. How agents talk to each other
--------------------------------
In coded team mode, agents do not directly chat with each other. Python passes
information forward by constructing prompts from prior outputs.

The data handoff chain is:

1. User prompt enters _run_coded_team_workflow(...).
2. Python loads/creates .vibedev/plan.md.
3. Optional knowledge curator gets a prompt containing:
   - summarized user request
   - current Python-owned plan
   - current common knowledge draft
4. Python writes the curator report into .vibedev/common_knowledge.md.
5. Optional business analyst gets:
   - full user request
   - pointer to common knowledge, if enabled
   - current Python-owned plan
6. Python parses the analyst's Proposed Tasks, appends new plan tasks, and keeps
   the full analyst brief.
7. Developer gets:
   - selected task
   - common knowledge pointer, if enabled
   - analyst brief and acceptance criteria, if present
   - prior tester report on retry attempts
8. Tester gets:
   - selected task
   - common knowledge pointer, if enabled
   - analyst brief and acceptance criteria, if present
   - developer report
9. README updater gets:
   - completed task
   - common knowledge pointer, if enabled
   - developer report
   - tester report

This means communication is mediated by:

- prompt text built in core.py
- files in the shared workspace
- .vibedev/common_knowledge.md
- the developer/tester reports returned from query(...)

The full contents of common_knowledge.md are usually not pasted into prompts.
Instead, prompts include the path and purpose of the file, so agents can read it
when useful.

In fallback manager mode, communication is SDK-native: the manager receives an
agents=... dict and can delegate to subagents through Claude Code's agent/task
mechanism. Python does not inspect intermediate subagent handoffs in the same
structured way.


7. Plan file and task selection
-------------------------------
Coded team mode uses:

    <workspace>/.vibedev/plan.md

The plan format is:

    # vibedev plan

    ## Goal
    <short goal>

    ## Tasks
    - [ ] Pending task
    - [x] Completed task

    ## History
    - <date> - Request: ...
    - <date> - Completed: ...
    - <date> - Blocked: ...

Python owns this file in coded team mode. Agents are told not to edit it.

_load_or_create_team_plan(...) does the plan setup:

- If the file exists, parse it.
- If not, create a new _TeamPlan.
- Compact verbose prompts into shorter goal/task/history text.
- Add the current request as a pending task if missing.
- Append a history entry for the request.
- Write the plan back to disk.

Task selection:

- First, _current_request_task_index(...) tries to find the current request's
  matching pending task. This prevents old pending backlog from stealing a new
  explicit user request.
- If no current-request task is found, _next_pending_task_index(...) selects the
  first pending task.
- If no pending tasks exist, the coded workflow returns without doing more work.

If the business analyst proposes new tasks, Python parses only the
## Proposed Tasks section and appends missing tasks. When the selected parent
task later passes, Python also marks analyst-added tasks from that review as
done.


8. How pass/fail works
----------------------
Pass/fail is enforced only in the coded developer/tester workflow.

The main loop is:

    for attempt in range(1, MAX_TEAM_FIX_ATTEMPTS + 1):
        run developer
        run tester
        parse tester verdict

MAX_TEAM_FIX_ATTEMPTS is currently 3.

Tester verdict parsing happens in _extract_verdict(...). It scans all response
lines and returns:

- True if the last explicit verdict is VIBEDEV_VERDICT: PASS
- False if the last explicit verdict is VIBEDEV_VERDICT: FAIL
- None if no explicit verdict appears

On PASS:

1. Python marks the selected task done in .vibedev/plan.md.
2. Python marks analyst-added tasks from that review done.
3. Python saves the plan text.
4. Python runs the README updater.
5. Python restores .vibedev/plan.md if the README updater changed it.
6. Python refreshes common knowledge if enabled.
7. The workflow returns successfully.

On FAIL:

1. The tester report is saved in memory.
2. The next developer prompt includes that tester report.
3. The developer is instructed to fix without weakening behavior or deleting
   useful tests.
4. The loop repeats, up to MAX_TEAM_FIX_ATTEMPTS.

On missing verdict:

1. Python wraps the tester output with a message saying the tester did not
   provide VIBEDEV_VERDICT: PASS.
2. That is treated as failed/inconclusive verification.
3. The developer gets the wrapped report on the next attempt.

After all attempts fail or remain inconclusive:

1. _record_plan_blocker(...) leaves the task pending.
2. A Blocked history entry is appended with a compact tester-report summary.
3. RuntimeError is raised.

The key invariant is: Python marks a task [x] only after the tester returns
VIBEDEV_VERDICT: PASS.


9. Common knowledge
-------------------
When common_knowledge=True and the coded workflow is active, Python writes:

    <workspace>/.vibedev/common_knowledge.md

The content is generated by _build_common_knowledge(...). It includes:

- project goal
- current request
- important paths
- current plan
- recent plan history
- optional curated project context from the knowledge curator
- known documentation files
- known tests
- notable project files
- team workflow rules
- agent notes

The file discovery intentionally ignores internal/cache directories such as:

- .vibedev
- .git
- .mypy_cache
- .pytest_cache
- .ruff_cache
- .venv
- __pycache__
- node_modules
- venv

The knowledge curator runs before analyst/developer/tester work. It reads the
workspace and returns structure-only Markdown. Python writes that report into
the common knowledge file. The curator does not edit files directly.

Users can disable this with:

    vibedev.set_common_knowledge(False)

or:

    vibedev "...prompt..." --no-common-knowledge

When disabled, Python skips the common knowledge file and skips the curator.


10. Logging and transcripts
---------------------------
Each run creates two log files next to the workspace, not inside it:

    <workspace>.vibedev-logs/<UTC>.log
    <workspace>.vibedev-logs/<UTC>.conversation.md

The reason they are outside the workspace is important: generated agents run
with cwd set to the workspace. Keeping transcripts outside prevents agents from
reading prior logs as ordinary project context.

_TranscriptLogger writes the forensic log. It records every SDK message and
captures:

- text blocks
- thinking blocks
- tool_use blocks with JSON input
- tool_result blocks with tool_use_id
- selected result metadata such as subtype, is_error, session_id, duration_ms,
  and num_turns

_ConversationLogger writes a lightweight handoff log. It records:

- run metadata
- the user prompt
- each stage label
- the exact prompt Python sent to that stage
- the final text response returned by that stage

It intentionally omits thinking, tool calls, file reads, and shell output.


11. README updater
------------------
After a coded team task passes, Python runs a README updater agent using
README_UPDATER_SYSTEM_PROMPT from core.py.

The README updater is told:

- planning, implementation, testing, and checkoff are already done
- update README.md only
- do not edit .vibedev/plan.md
- do not implement feature code

Python protects the plan file by saving the expected plan text before running
the README updater and restoring it afterward if changed.

13. Current sharp edges and observations
----------------------------------------
1. In coded developer/tester workflow, duplicate developers/testers do not
   create parallel workers. Python selects the first matching developer and
   tester model. Duplicate roles matter in fallback manager mode because
   subagents_for(...) assigns unique SDK keys.

2. Fallback manager mode has weaker guarantees. It can delegate to agents, but
   Python does not enforce the tester PASS gate unless both developer and tester
   are configured and the coded workflow is selected.

3. The workspace is reused directly. This is good for resumability, but it means
   generated artifacts and old state can influence later runs.

4. Long-running processes are handled by prompt discipline, not by a Python
   process reaper. Role prompts tell agents not to leave servers/watchers alive,
   but subprocesses spawned by Claude Code are not directly owned by vibedev.

5. claude-agent-sdk / Claude Code CLI must be installed and authenticated for
   real agent runs. Tests mostly monkeypatch query(...) or inspect pure Python
   helpers, so they do not prove live SDK authentication.


14. Short mental model
----------------------
For a normal robust run, configure developer + tester:

    vibedev.set_team(["developer", "tester"])
    vibedev.prompt("build ...")

Then vibedev behaves like this:

    user prompt
      -> Python plan file
      -> optional common knowledge + curator
      -> optional business analyst review
      -> developer attempts one selected task
      -> tester verifies developer report
      -> PASS marks plan done and updates README
      -> FAIL feeds tester report back to developer and retries
      -> repeated failure records a blocker and raises

For a team of one developer, vibedev behaves like this:

    user prompt
      -> fallback manager prompt
      -> SDK-native developer subagent delegation
      -> manager reports completion/limitations

The strict pass gate exists in the first model, not the second.
