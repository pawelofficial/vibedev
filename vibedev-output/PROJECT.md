# sql_lineage

A backend library that parses a SQL schema file (DDL + views) with sqlglot, builds typed data-models for every table/column/view, resolves column-level lineage across views, and exposes a catalog API ready for a visualization layer. The default dialect is None (sqlglot generic), NOT the unsupported "ansi" string, fixing the sqlglot 30.8.0 incompatibility identified by the tester.

_Generated by vibedev from the prompt: "Create a parser for schema.txt file using sqlglot that will be later on used to visualize column lineage of the sql tables and views. Create a good parsser that will support visualization later on, but no visualization yet - backend structures only for now."_

## Files

- `sql_lineage/exceptions.py` — All custom exception types for the sql_lineage package. Kept in their own file so every other module can import them without creating cycles.
  - components: SchemaParseError, UnresolvedReferenceError, CircularDependencyError
  - depends on: none
- `sql_lineage/normalizer.py` — Single utility function that normalises SQL identifiers: strips ANSI double-quotes, MySQL back-ticks, T-SQL square brackets, then lowercases and strips surrounding whitespace.
  - components: normalize_name
  - depends on: none
- `sql_lineage/models.py` — Immutable (frozen) dataclasses and one mutable container that together form the complete in-memory representation of a parsed schema and its column-level lineage graph.
  - components: ColumnRef, ForeignKeyDef, TableDef, ViewDef, LineageEdge, SchemaGraph
  - depends on: none
- `sql_lineage/parser.py` — SchemaParser: reads a schema file (or SQL string), delegates to sqlglot for AST parsing, and populates a SchemaGraph with TableDef and ViewDef objects. Does NOT resolve column lineage — that is the resolver's job. IMPORTANT: default dialect is None, not 'ansi', to be compatible with sqlglot 30.8.0.
  - components: SchemaParser
  - depends on: sql_lineage/exceptions.py, sql_lineage/normalizer.py, sql_lineage/models.py
- `sql_lineage/resolver.py` — LineageResolver: takes a fully populated SchemaGraph (tables + views, no edges yet) and resolves column-level lineage for every view. Mutates graph.edges in-place. Views are processed in topological order so that lineage from upstream views is available when resolving downstream ones.
  - components: LineageResolver
  - depends on: sql_lineage/exceptions.py, sql_lineage/normalizer.py, sql_lineage/models.py
- `sql_lineage/catalog.py` — SchemaCatalog: a read-only query interface built over a resolved SchemaGraph. Provides entity lookups and both direct and transitive upstream/downstream column lineage queries via BFS. Intended as the primary API for a visualization layer.
  - components: SchemaCatalog
  - depends on: sql_lineage/models.py, sql_lineage/exceptions.py
- `sql_lineage/__init__.py` — Public API entry point. Exports parse_schema(), which orchestrates parser + resolver + catalog in one call, plus all public symbols so callers only need 'from sql_lineage import ...'.
  - components: parse_schema
  - depends on: sql_lineage/exceptions.py, sql_lineage/models.py, sql_lineage/parser.py, sql_lineage/resolver.py, sql_lineage/catalog.py, sql_lineage/normalizer.py
